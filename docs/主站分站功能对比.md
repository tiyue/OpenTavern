# OpenTavern 主站与分站功能对比

核对日期：2026-10-01（北京时间）。本报告只做功能审计，没有修改应用、发布站点、发送模型请求或读写云同步数据。

## 1. 结论

分站保留了基础聊天、群聊、角色卡、世界书、自动与手动总结、两阶段生成等核心功能，但尚未跟上主站在以下方向的扩展：

1. **可靠性保护**：摘要源消息校验、重生成历史与失败恢复。
2. **提示词管理**：多预设库、独立正则管理、Author's Note、角色 Depth Prompt、请求诊断。
3. **聊天操作**：消息收藏、全文搜索、续写、以用户口吻生成、现有会话成员管理、多开场切换。
4. **复杂角色卡兼容**：Markdown/HTML 渲染、MVU 状态与声明式模板、分级沙箱运行时。
5. **扩展与阅读体验**：TTS、阅读宽度/字号、背景图片、桃信主题、启动恢复上次聊天等。

不是所有不同都应该补回：本地推理和顶部语言/GitHub 按钮是此前明确要求移除的；ComfyUI 被另一套图片网关替换。分站还有主站此次公开前端中未发现的 D1 云同步实现。

**角色卡目录没有发现缺项**：两边公共目录均为 157 张，贡献者目录均为 41 张，合计 198 张。目录一致不代表逐张卡片正文也完全一致。

## 3. 需要优先关注的可靠性差异

这些是代码层面确认的机制差异，不是本次已经复现的线上故障，也不能直接解释之前的所有“消失、失败、格式不对”。

### F01：摘要有效性与源消息绑定

主站摘要保存源消息 ID 和修订信息，区分有效、无效、未验证状态。编辑、切换回复版本等改变原消息后，会检查摘要是否仍能替代对应原文；无效或未验证摘要不直接当成有效覆盖。

分站摘要目前主要保存 `coveredStart` / `coveredEnd` 数字范围。已有区间并集、阈值和并发防重逻辑，但没有主站这套消息修订校验。编辑旧消息的流程也未使关联摘要失效。

影响：修改已总结的内容后，模型可能继续收到旧摘要；删除历史导致下标变化时，数字区间与原内容的关联需要额外保护。这里是静态发现的风险，不是已完成故障复现。

证据：主站 `validSummaryCoverage`、`captureSummarySources`、`invalidateSummariesForMessage`；分站 [摘要写入](../src/app/summary/54-summarization-runtime.js)、[历史裁剪](../src/app/prompt/41-prompt-history-messages.js)、[消息编辑](../src/app/chat/67-message-edit-helpers.js)。

### F02：回复生成历史与失败恢复

主站保存 `responseVersions`，提供历史版本入口、版本切换及重生成失败恢复。重生成准备阶段虽然也会移除当前展示消息，但事先保存原回复及关联消息，失败路径可以恢复。

分站支持重新生成，却没有这套回复版本库。当前**主回复**重生成流程先移除旧主回复和关联二阶段消息，再发请求；错误处理主要恢复界面状态，没有恢复旧主回复的备份路径。

影响：主回复重生成失败后，旧回复缺少恢复保障，应优先补齐。不能把这个结论扩大成“二阶段重生成也一定删旧内容”：分站最近的二阶段修复已保留旧结果直到新结果校验并保存成功。

证据：主站 `prepareResponseRegeneration`、`restoreFailedResponseRegeneration`、`switchResponseVersion`；分站 [主回复重生成入口](../src/app/chat/67-message-actions-ui.js)、[旧消息移除](../src/app/chat/67-message-action-helpers.js)、[重生成错误处理](../src/app/chat/67-message-regeneration-runtime.js)。

### 4.3 消息渲染与复杂角色卡

| 编号 | 功能 | 主站公开实现 | 分站当前实现 | 建议 |
| --- | --- | --- | --- | --- |
| F17 | Markdown 与通用 HTML widget 渲染 | GFM Markdown、安全清洗、分段识别 HTML widget、样式隔离；脚本组件另走沙箱 | 主要是文本转义、对话高亮、选项 XML 和特定状态栏 `<details>`；不是通用 Markdown/HTML 渲染器 | P1 |

| F19 | 分级角色卡前端运行时 | 分级授权、隔离 iframe、固定依赖/校验、宿主能力接口；联网层另用独立 origin、域名授权、配额和审计 | 角色卡/预设只执行声明式正则，不执行其 JavaScript；没有对应的 iframe/RPC/授权运行时 | 单独评估，不宜直接照搬 |

尤其 F19：主站代码对 Android/WebView 最高限制为 L2；L3 需要独立 HTTPS origin，且本次没有验证该服务可用。不应描述成主站能执行任意脚本、兼容全部 SillyTavern 插件，或全部手机都能使用联网层。

## 6. 主动移除、替代实现与分站扩展

| 项目 | 实际差异 | 处理建议 |
| --- | --- | --- |
| 浏览器本地推理/WebLLM | 主站仍有；分站按此前要求移除 | 保持移除，不作为待修缺口 |

## 7. 建议补齐顺序与验收重点

### 第一批：可靠性保护

- F01 摘要源消息身份、修订和有效性；F02 主回复版本历史与失败恢复。
- 验收：编辑/删除已总结消息后不继续误用旧摘要；主回复重生成失败恢复旧正文和关联二阶段结果；重复触发不产生重复请求；跨会话请求仍写入发起会话。
- 兼容要求：旧数字范围摘要不可直接丢弃或无条件当成新格式有效；消息 ID 和云同步数据应有明确迁移规则。

### 第二批：日常聊天与提示词管理

- 收藏/搜索、多开场、已有会话成员管理、续写；多预设库、正则管理、Author's Note、Depth Prompt、请求诊断与总结参数。
- 验收：搜索/收藏能定位长历史中的正确消息；切换预设可持久保存；预览不意外修改变量；笔记和深度注入与实际请求一致；备份及 D1 同步覆盖新增普通数据，不包含凭据。

### 第三批：复杂卡片兼容

- 先补安全 Markdown/静态 HTML，再补 MVU/声明式模板；可执行脚本与联网卡片单独设计授权方案。
- 验收：文本、XML 选项和原有状态栏不回归；不可信 HTML 不越权；变量更新能正确回放；脚本不能直接读宿主密钥；移动端有清晰降级和权限边界。
- 不要通过解除安全清洗、直接执行卡片 JavaScript 或整页替换来追求表面一致。

### 第四批：可选扩展与便利设置

- TTS、背景、桃信主题、阅读参数、启动恢复、设置草稿取消与更细的备份选择。
- 验收：桌面与移动端、浅色与暗色可用；TTS 使用真实供应商验证成功/失败/取消及 CORS；新增本机密钥不得进入云同步。

本次没有实施这些建议，也没有估算“一比一完成百分比”。若接下来要求开发，应按上述批次逐项确认范围并用旧数据副本回归，而不是一次覆盖整个应用。
